How to improve (minimal + scalable)
Use a single state object.

const state = {
  currentView: 'profile',
  userProfile: null,
  userPosts: [],
  loading: { profile: false, posts: false },
  requestId: { profile: 0, posts: 0 }
};

Only update state in one place (e.g., setState(partial)), then call render().
Using a state object helps because it centralizes all mutable data into a single source of truth.
 In this dashboard, that prevents race conditions from async fetch calls, avoids rendering with incomplete data, and makes it easy to guard UI updates based on the current view. 
 It also improves testability because functions no longer depend on global variables.”

 “State doesn’t stop async responses;
  it stops stale responses from rendering by checking whether the current state still matches the user’s intent.”

let profileReq = 0;
async function fetchUserProfile() {
  const reqId = ++profileReq;
  const res = await fetch("/user/profile");
  const data = await res.json();
  if (reqId !== profileReq) return;          // ignore stale response
  userProfile = data;
  if (currentView === 'profile') renderProfile();
}

also while request is in progress render 'loading' / only render when data present.

2b) “How can we assume DOM has latest data?”
Right now, you cannot assume that:

You render before data arrives (renderProfile() runs with userProfile === null)
Old network responses can overwrite newer UI (see race conditions below)
Event handler duplication causes multiple updates

Why this duplicates handlers
renderProfile() is called:

after fetch resolves (fetchUserProfile().then(... renderProfile()))
and also from renderView() (often on hash changes)


Each call replaces DOM via container.innerHTML = html; and then attaches listeners again
Worse: the "saveProfileBtn" listener is attached inside the "editProfileBtn" click handler.

So if the user clicks Edit 3 times, you attach 3 Save handlers.
Next Save click triggers updateProfile() 3 times (duplicate API calls + weird UI).

Fix:
“I’d put a loading guard in renderView() so we don’t render before data exists, and 
I’d move click handlers out of renderProfile() into a one-time delegated listener in initDashboard() (or overwrite with onclick) to prevent duplicate Save calls.”


2c.
c. DOM Manipulations and Improvement Suggestions
=> Issue 1: What is the issue
The code builds UI using large innerHTML strings. Every time innerHTML is set, the browser destroys and recreates the entire DOM subtree.
Fix
Prefer DOM APIs like createElement, appendChild
Or use templates (<template>) instead of string concatenation
In frameworks, use declarative rendering

=>Issue 2: Inconsistent element IDs
What is the issue
HTML uses id="edit ProfileForm" (with a space) while JS queries editProfileForm (no space).

=>Issue 3: Event listeners are rebound on every render
What is the issue
renderProfile() attaches click listeners every time it runs.
Worse, the Save button listener is added inside the Edit button click handler.
Why this is bad
Every render adds new listeners
Clicking Edit multiple times stacks Save handlers
One Save click triggers updateProfile() multiple times

Fix
Bind event handlers once using event delegation (in initDashboard)
Or overwrite handlers using onclick instead of addEventListener

=> Issue 4: XSS risk due to raw HTML injection
What is the issue
User data (name, email, post.content) is injected directly into innerHTML.
Why this is dangerous

If data contains HTML or scripts, the browser executes it
Creates a Cross-Site Scripting (XSS) vulnerability

Fix

Use textContent instead of HTML concatenation
Treat all external data as unsafe by default



Issue 5 => 

Posts are rendered using container.innerHTML += ... inside a loop.
Why this is inefficient

Each iteration re-parses and re-renders the entire container
Causes layout recalculations repeatedly
Scales poorly for large lists

fix: “DocumentFragment 
lets us build all DOM nodes in memory without triggering reflow, and then append everything once, avoiding the repeated re-parsing and repaint caused by innerHTML += in loops

3a
     Potential race conditions / async issues in fetching
    Race: out-of-order responses
    
    Suppose you call fetchUserPosts() twice (hash change, re-render, user clicks quickly).
    Request A (older) returns after Request B (newer).
    Older response overwrites the latest state (because both write to the same global).
    Another async issue: “wrong view update”
    While you’re on Profile, Posts fetch finishes and calls renderPosts().
    UI suddenly shows posts even though URL says #profile.

3b.
    b. Rapid View Switching & UI Inconsistencies
    Why rapid view switching causes UI inconsistencies
    Scenario interviewers love:
    User clicks Posts → currentView='posts', starts fetchUserPosts().
    Immediately clicks Profile → currentView='profile', renders profile.
    Posts API returns late → .then() runs → calls renderPosts() anyway.
    ✅ Result: URL is profile but UI shows posts (“ghost update”)
    The URL and the UI are now out of sync.

3c. How can we get the latest response from API.
“I add a request counter inside fetchUserProfile and fetchUserPostsand increment it before making the fetch call. I store that incremented value in a local variable. 
When the response comes back, I compare that local id with the latest id. If it doesn’t match, it means this response is old, so I ignore it and don’t update state or DOM.”
