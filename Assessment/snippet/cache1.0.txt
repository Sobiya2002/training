CODE FLOW: 
The entire code is wrapped inside an Immediately Invoked Function Expression
Inside the IIFE, several functions are defined and exposed through window.app.

When app.main() is executed, two asynchronous operations are initiated concurrently: fetchData("api/data") and fetchData("error").

The fetchData() function returns a Promise and uses setTimeout() to simulate a network request with a one-second delay.
For the "api/data" request, it first checks whether data already exists in the cache. Since this is the first request, the cache is empty, so a simulated response is created,
stored in the cache object, and the Promise is resolved with that data.

The first .then() handler receives the data, logs it, and passes it to processData(). Inside processData(), the helper function compute() reverses the string 
and returns the processed result. The processing time and reversed string are then logged.

After that, fetchData("api/data") is called again. This time the cache already contains the response, so the cached value is returned instead of creating a new response. The next .then() logs the cached data.

In parallel, the second request calls fetchData("error"). After the simulated delay, the code intentionally rejects the Promise because the endpoint equals "error". Control moves to the .catch() block, which logs the error.

Finally, every fetchData() call includes a .finally() block that executes regardless of whether the Promise is resolved or rejected, making it useful for cleanup or completion logging.

What performance issue will arise in the current implemtnation
The main asynchronous performance issues are inefficient cache utilization, duplicate concurrent requests, and potential event-loop blocking from synchronous processing. These can be addressed by returning cached responses immediately, sharing in-flight Promises across concurrent requests, and offloading CPU-intensive work from the main event loop. Additionally, introducing cache expiration helps prevent memory growth in long-running systems.

- What improvements can be made to the asynchronous design to further optiatia perforee under heavy load?
Asynchronous Performance Optimizations
1. Return Cached Data Immediately Instead of After Delay
Where: Cache lookup happens inside setTimeout, so cached requests still wait 1 second.

Fix: Check the cache before scheduling asynchronous work and return a resolved Promise immediately.

Benefit: Reduces latency for cache hits and decreases unnecessary timer creation under heavy load.

2. De-duplicate Concurrent Requests Using In-Flight Promises
Where: Multiple parallel requests to the same endpoint create separate setTimeout calls and duplicate work before the cache is populated.

Fix: Maintain an inFlightRequests map keyed by endpoint. If a request is already in progress, return the existing Promise instead of creating a new one. Remove the Promise from the map in finally() once the request completes.

Benefit: Prevents duplicate asynchronous operations, reduces resource usage, and improves scalability under concurrent load.

3. Avoid Blocking the Event Loop with Synchronous Processing
Where: processData() performs CPU-intensive work synchronously, which can delay timers, Promise callbacks, and other requests as data size grows.

Fix: Break large workloads into smaller chunks and periodically yield to the event loop, or offload heavy processing to a Worker Thread/Web Worker.

Benefit: Keeps the application responsive and prevents long-running CPU tasks from blocking asynchronous operations.
