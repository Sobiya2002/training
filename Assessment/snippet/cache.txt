Discuss:

- What performance issues might arise from the current implementation?

Unnecessary latency even for cached data
Where: Cache check is inside setTimeout in fetchData, so cached responses still wait 1 second.
Fix: Move the cache check before setTimeout and return cached data immediately to get real performance benefit from caching.

Process Data issue: processData runs synchronously on the main thread; under heavy data or high frequency it can block the event loop and delay all async work,
 so heavy processing should be offloaded or broken into smaller chunks / use worker threads.

 Why this is a problem under load
Right now, your data is small, so it feels harmless.
But imagine:

data is very large (big string / JSON)
processData is called many times
multiple fetches resolve around the same time

What happens then?
Event loop timeline:

| processData running | processData running | processData running |
(no timers, no promises, no UI updates can run here)

While processData is running:

setTimeout callbacks cannot run
Promise .then() callbacks are delayed
UI may freeze (in browser)

✅ That is what “blocking the event loop” means

Fetch Data Issue: Multiple concurrent calls to the same endpoint all schedule separate timers and duplicate work; 
tracking in‑flight requests and reusing the same Promise avoids redundant processing and scales better under load.

Where the issue is in your code
Every call to fetchData("api/data") does this:
JavaScriptsetTimeout(() => {  // work}, 1000);
There is no check for:

“Is this request already in progress?”
You keep a structure like:
